# One-query lifecycle and accounting contract — proposed, fixture-only

Version: P02F-cost-fixture-v1. Not a serving policy adoption or executable model plan. No model backend exists in the new module. Real supervisor and direct worker entry points unconditionally reject; a caller-supplied authorization cannot enable them. Historical P02D authority is consumed and its files stay unchanged.

## Timeline and boundary

Use a supervisor monotonic clock, with event timestamps and durations rather than subtracting unrelated child clock origins. Start t0 **before** the first query-specific validation/admission or source-binding work. Finish t1 only after mandatory response handling and confirmed safe stop. Every attempted query includes early rejection costs. A pre-admission retry ceiling of zero does not make a failed attempt free. Unknown process termination leaves C_time null and observed elapsed as a lower bound, with future reconciliation required; never report the lower bound as complete cost.

The proposed exclusive phases are: validation/admission; process startup and necessary source/checkpoint checks; load; original-question tokenization; service feature; cheap observables; CPU head/calibration/action/dispatch; selected prompt preparation; full answer RNG reset; sole answer; strict handling/response publication; cancellation if needed; safe termination/cleanup; final mandatory response acknowledgment. A non-overlapping residual covers uninstrumented gaps. Load/tokenization/feature/answer sub-timers and CPU/GPU synchronization can be nested inside these intervals; do not sum nested timers into the exclusive total. Overlapping worker and parent work is one service interval, not two charges. No claim of pure GPU time.

All required validation, state integrity and safe-response checks stay inside the proposed boundary. Gold-dependent native scoring and long-term research archive verification may be separate only because they are not needed to answer that query. They still retain their own full research timing. Decoding, native-channel/FINAL/syntax validation and mandatory safe-response checks remain serving work. This slice does not refactor the existing combined generate/parse/native-score function or change its scientific behavior. A later reviewed implementation would need to separate timers without changing the parser/scorer outcome.

Keep the existing cost-row algebra C_gate+(1-g)C_D+g C_R. A prospective non-overlapping allocation would put the one common load/startup and required terminal handling in the selected service-package charge, with the extra feature/head/calibration work in C_gate, not charge the load twice. But the timing distribution of an answer following a feature pass need not equal that of a bypass answer. Reusing measured bypass means as active-path C_D/C_R would require reviewed consistency evidence or a declared matched cost-collection design. D16 remains open; neither component subtraction nor a proposed allocation establishes that missing equivalence. Tariff bundles can define additive price semantics explicitly while physical side effects remain descriptive.

The final cost-report file may be written after the service boundary as research bookkeeping, but the served response and terminal decision must already be durably committed and acknowledged. If the cost report cannot be recorded, evidence is unresolved; no fabricated successful cost/score row. Any mandatory serving publication moved into that final report must instead be included in t1. Source/checkpoint checks required per query cannot be shifted to an uncharged preparation phase.

“Cold process” means a fresh process and one charged model initialization per query; filesystem/OS/device/thermal caches are not claimed cold. No persistent service is implemented. Shared initialization across unrelated queries would need a fixed session policy and allocation for unused capacity, failures/restarts and cleanup, shared identically by every comparator and reference. It is not a shortcut adopted here.

## Feature, fixed action, and common future gate interface

Preserve the exact reviewed `p02d-input-only-v1` recipe: cached pinned tokenizer on original question with no special tokens/truncation; same Qwen3-8B decoder, final post-RMSNorm hidden state, mask-weighted float32 mean, float32 width 4,096, evaluation/inference mode, use_cache=False and no past keys. The nine approved observables and their Unicode/regex conventions remain in the immutable `p02d_features.py`; no new feature search or normalization fitting.

A future common head interface takes **embedding[4096] and the ordered nine input-only observables**. Input ID is join metadata outside the learned input. Original text is available only to the approved feature/tokenization layer. No family, source filename, latent fields, gold, score, failure, trace or answer preview enters the head. The interface returns method-specific raw/calibrated values and the chosen D/R action, plus separately measured CPU/head/calibration/dispatch timing and head/config hashes. TC, winner and factorized differ only in their approved heads/rules under reviewed parity; architecture, parameters, transforms, calibration, head operation ceiling and measured head cost remain unresolved. No synthetic neural head is benchmarked here.

The prototype instead records a **fixed action** and `head_cost_seconds=null`, `learned_gate=false`. It is not TC/winner/factorized inference. The service-feature pass is still required for an active-gate-shaped D query. An audit-fallback D path bypasses feature/head work completely; the fixture has an explicit bypass path to test this distinction, but measures no real bypass reference.

One model load may serve the input-only passes and sole answer within the same proposed query. Each pass needs fresh IDs/masks; no past keys, retained hidden states or cached prefill can seed the answer. Native D/R mode serialization is unchanged. Reset all relevant answer RNGs from its unique future stream immediately before the one admitted generation, after feature work. Fixture calls check order/flags and independent buffers by identity labels; they do **not** verify tensors, exact token serialization, numerical GPU equivalence or RNG behavior on the checkpoint. Those remain future reviewed implementation/measurement requirements. No actual native question/request/seed is created here.

## Warm-ups and reservations

The unapproved diagnostic proposes 24 cold workers, 24 service feature passes and two extra warm-ups in the first worker, then one answer per worker. All 26 forwards cost research work. Both warm-ups occur on the first two prespecified inputs and are separately timed; the first query's inclusive interval includes them. It is flagged as a warm-up-augmented diagnostic query, retained without dropping or pretending that subtracting two intervals yields a measured cold reference. Every query still pays its own service feature. Later queries can have different unspecified machine-cache conditions.

The ordinary reservation arithmetic is 150 load + 120 feature + 120 answer + 10 cancellation grace + 30 cleanup = **430 seconds**, leaving **20 seconds** in the 450 reservation. The first adds two ×120 warm-ups: **670 seconds**, leaving the same 20 in 690. At most one failed operation needs cancellation because a failed feature/load stops before answer; otherwise charging repeated cancellation stages would need a different reservation. This is only nominal arithmetic. Startup/source checks, tokenization, CPU head, prompt prep, response publication and bookkeeping have no justified aggregate 20-second limit. There is also no proven bound on cleanup after the configured wait. **The reservations cannot presently be certified as conservative for the entire intended timeline.** We do not enlarge them, claim support, or publish a live plan.

Discrete totals remain 24 answers ×2,048 =49,152 reserved output tokens; 26 forwards ×2,048 =53,248 maximum input positions. Proposed operational limits remain 5,400 worker seconds, 7,200 wall seconds, 128 MiB including packet; J=0, no replacement, no answer warm-up. The aggregate need not cover every slot at all deadlines. A future reviewed controller must reserve available time/tokens/evidence before each new admission, observe actual overshoot and safely close incomplete runs. Reservations are control fields, never substituted for realized expenditure or c_max.

## Immutable records and recovery

Record schema: protocol/version, evidence kind, query/slot identity, source/plan/authorization hashes when a real plan exists, event kind, monotonic start/end, phase owner, exclusive or parent interval, validity status, consumed/admitted flags, counts, reservations, observed elapsed, safe-stop status, residual, unknown cost and incident reference. Actual token counts and unknown counts must be distinct from cap reservations. Fixture envelopes bind kind/identity/payload hash.

Reuse the reviewed P02D same-directory hard-link publication: serialize, flush and fsync a private `.pending` file, then atomically create the final name with `os.link`; duplicate final names fail. Readers consume only final names and validate JSON/identity/hash; only absence is pending. No overwrite or parser-error retry fallback. A crash before claim publication admits no work; a crash after durable claim consumes the slot even if no result is committed. Incomplete/corrupt records block affected recovery. File durability is not a universal power-loss/directory guarantee.

The minimal fixture scans only its own small registry, never the accepted P02D research ledger. It records no-replay claims and exact final resources once; repeating recovery does not charge again. Missing final records leave cost unknown, not zero. It is **not** a new online recovery system. A later real implementation would need a small per-run authoritative append-only journal or checkpoint with anchored prefix hashes, incremental head verification, exclusive writer ownership, child admission tokens and offline reconciliation. Full historical revalidation must remain available, but should not accidentally be repeated on every serving heartbeat. This redesign is described, not implemented, because the cost decision is blocked.

Known retained answer failures and safe deadlines are distinct from software/evidence incidents. Feature failure prevents answer admission. Unsafe cleanup dominates an initiating resource stop. Uncertain admissions never replay. Synthetic fixture scores are oracle labels for testing these cases, explicitly **not** native rescoring or new observations. Committed malformed/hash-invalid JSON fails closed. A writer interruption leaves an unpublished temporary file or an unresolved consumed claim; no process is silently declared stopped.

## Implemented scope and limits

`src/taskcognition/p02f_cost_v1.py` contains only public live rejection, a closed ScriptedWorker/FakeClock implementation, record publication/read validation, fixture recovery and interval reconciliation. It accepts no inference backend/callback. Files are confined to `artifacts/fixtures/`; output provenance says fixture. Its elapsed values are deterministic synthetic seconds, not timed Windows service work; actual file IO used to test publication is not represented as empirical service cost. It cannot be promoted to a live runner by an authorization flag. Exceptions before final publication leave a consumed/unknown record for fail-closed recovery; no background model process can exist.

An injected answer duration beyond the 120 deadline is retained as a safe timeout or unsafe integrity incident, with uncut elapsed/overshoot. Fake-clock success checks bookkeeping only. It cannot prove finite support, reservation sufficiency, timing stability, actual cancellation guarantees or scientific feasibility. No test result resolves D08/D09.
